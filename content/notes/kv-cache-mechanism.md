## Reusable-state

前置知识是[因果自注意力](attention-qkv.md)及[逐 token 生成](transformer-generation.md)。讨论固定参数、相同前缀、相同位置和注意力规则、关闭随机训练操作的标准因果模型。浮点计算实现差异可能产生微小数值差别。

在每一层，历史位置 $i$ 只能依赖 $x_{\le i}$。追加新 token 不改变这些输入，也不允许历史位置读取新 token。因此历史隐状态保持相同，由它投影得到的 $k_i,v_i$ 也相同。这一层的论证逐层成立，于是各层历史 KV 都可复用。缓存的直接实现依据见[GPT-2 attn 与缓存文档](../sources/foundations-kv-systems.md#cache)。

对当前位置 $t$，只计算当前的 $q_t,k_t,v_t$，把新 KV 追加到各层缓存：

$$
K_{\le t}=[K_{<t};k_t],\qquad V_{\le t}=[V_{<t};v_t],\qquad
o_t=\operatorname{softmax}\left(\frac{q_tK_{\le t}^{\top}}{\sqrt{d_k}}\right)V_{\le t}.
$$

历史 Q 用于历史位置自己的输出，而当前输出只需要当前 Q 与全部可见 KV。历史输出已经处理完毕，继续保存历史 Q 对标准逐 token 解码没有必要。这是数据依赖关系的结果，不是 Q 的大小与 KV 不同，也不是禁止其他算法存储 Q。

## Prefill-and-decode

Prefill 一次处理提示词，计算各层 KV，并从最后一个有效位置的 logits 选择第一个输出 token。随后每次 decode 将刚选出的 token 输入模型，生成它的 KV，再选择下一个 token。KV 尚未覆盖“刚从 logits 选出、还未送入模型”的 token；这是区分缓存长度与已输出长度时容易混淆的一步。

训练时整段标签已知，可以批量计算全部位置；标准缓存主要服务自回归推理。编码器—解码器模型还可复用不随解码步变化的编码器侧交叉注意力 KV，不能把所有缓存现象限制成 decoder-only 模型。

## Cost

下面是对稠密全上下文注意力的算术计数，固定层数和头数，不是实测延迟承诺。设当前上下文长度为 $t$、模型宽度为 $d$：

| 计算范围 | 主要注意力计算 | 线性层和 MLP 的代表性开销 |
|---|---|---|
| 每步重跑整个长度 $t$ 的前缀 | $O(t^2d)$ | $O(td^2)$ |
| 缓存后只计算一个新位置 | $O(td)$ | $O(d^2)$ |

因此“二次变线性”描述的是这两种**单步**计算方式中的注意力部分。若从短序列持续生成至长度 $N$，缓存后的注意力累计为

$$
\sum_{t=1}^{N}O(td)=O(N^2d),
$$

而不是 $O(Nd)$。提示词长度为 $P$、另生成 $G$ 个 token 时，需另计 prefill 的 $O(P^2d)$ 和 decode 累积的 $O((PG+G^2)d)$；投影与 MLP 也应另计。缓存并未让当前 token 不再读取历史。

单请求、单 token 解码常把某些线性层计算变为向量乘矩阵；批量请求、多个新 token 或融合实现仍可能以矩阵乘法组织。GEMV/GEMM 的名字不能直接推出 decode 延迟总比 prefill 小；两者处理 token 数、并发量和内存访问方式不同。

## Memory

设批量为 $B$、层数为 $L$、历史长度为 $T$、KV 头数为 $h_{kv}$、每头维度为 $d_h$、每元素字节数为 $b$，完整 KV 数据的近似大小为

$$
M_{KV}=2BLTh_{kv}d_hb.
$$

系数二对应 K 与 V。这里不含分配碎片、元数据、其他激活和模型权重；分层配置不同时需逐层求和。固定其他条件时，长度和并发都使缓存线性增大。减少 KV 头数、精度或保存长度作用于不同因子，代价也不同。

## Validity

复用要求参数及前缀计算条件一致。修改历史 token、模型/适配器、位置处理或可见范围可能使后续缓存失效。双向自注意力追加输入后，历史表示通常也会改变，上述因果论证不成立。跨请求复用必须匹配可复用前缀及模型条件，不能只比较文本“意思相近”。

**工程延伸：**[缓存优化的不同目标](kv-cache-optimization.md)区分减少重算、减少实际 KV 数据、减少分配浪费与改变存储位置，解释缓存为何也会成为瓶颈。

## Approximate-reuse

**2026-10-16 新增候选边界。** 上述相同 KV 的论证依赖完整的前缀计算条件。RAG 若把检索文档分别计算的 KV 拼接起来，后面的块没有读取前面块的上下文，其状态一般不等于把全文一起 prefill 得到的状态。[CacheSmith §2.1–2.2](../sources/paper-cachesmith.md)以此区分精确前缀复用与近似分块复用。

因此，复用的字节数增加并不证明输出等价；选择哪些状态重算需要同时看任务质量与服务目标。CacheSmith 的离线需求分布代理用于规划复用/重算，并不是逐次在线输出正确性的证明。[逐请求质量与时延联合成功](storage-latency-and-slo.md#joint-success)解释如何评价这类取舍。本文未复现该系统，也没有将其任务分数当作所有语义正确性的保证。

## Residency-boundary

2026-10-20 AI 候选延伸：[驻留与可访问性](kv-cache-optimization.md#residency-and-accessibility)以本页字节公式估计跨调用保留状态，但生产模型保密时只能用替身几何。每 token 理论大小不包含会话终止/闲置回收、路由隔离、量化元数据或分配器碎片；这些是容量计划的额外前提，不能从因果复用证明推出。

## Hybrid-state-and-forks

2026-11-03新增AI候选：本页KV充分性的推导限于所述标准因果注意力模型。若模型还包含循环层，恢复某个前缀需有该边界的循环状态、短因果卷积窗口及全注意力层KV。[HiState的混合检查点](kv-cache-optimization.md#hybrid-checkpoints)解释为什么末尾循环状态不能裁回较短前缀；保留KV并不自动补出缺失的循环状态。

另一种复用发生在同一上下文要独立回答多个问题时。[Li等的Flide预印本](../sources/paper-flide.md)把各单题prompt逐token的最长公共前缀作为主干，将每道题作为独立分支。简单串接题目会让后题读取兄弟题；只改注意力掩码也不能从已融合的循环状态中移除先前兄弟题。

要保持每题与单独输入“主干+该题”相同的依赖，标准注意力只读取同请求的主干及自身分支，并遵守逻辑位置的因果和滑窗限制。每分支位置从主干末尾接续，不能用物理铺平后的总位置替代。GatedDeltaNet循环层则共享一次算出的主干末状态及卷积窗口，各分支从这个相同边界各自递推，兄弟题不串入历史。逐token投影、归一化和MLP不混合不同token，故在论文所述因果层和精确算术下，可逐层归纳得到每题输出等于隔离forward。它不是任意状态机只靠mask就可分叉的定理。

逻辑隔离允许更换物理执行方式。Flide用GPU元数据标明请求、分支、位置和有效长度，在已捕获的CUDA graph容量内铺平执行；尾部padding不能被有效token读取，超容量按请求拆分或对过大的单请求eager执行。这里减少重复主干和执行开销，未改变每题允许读取的信息。

语义等价还需与浮点结果分开。默认batch布局可以改变kernel和归约顺序，精确算术证明不意味着bit相同。作者可选invariant模式约束求和顺序及分支chunk边界，在同软硬件下测试随负载不变；不保证跨硬件恒同，也不等于答案正确。Flide的评价对象是选项对应输出行的概率，不是任意长文本生成。

[来源页的具体比较](../sources/paper-flide.md#comparison)保留单H200/BF16、闭环并发与基线版本：Qwen3.5-4B的RACE-all多题负载上，单客户端中位时延57.6→14.1ms，64客户端吞吐67→124请求/秒；单题QuALITY上差距较小。两负载不同，不能当共享比例的单变量消融。HiState和Flide各自补恢复与隔离条件，本轮没有证明两引擎已组合或可直接互换检查点。

## Rounding-and-execution

**2026-11-05新增AI候选。** 前面的因果性与分支隔离只确定允许依赖哪些状态；实际复用还需固定机器如何计算。[Lu等ExactLoop预印本指定部分](../sources/paper-exact-loop-serving.md)给出一条具体路径：融合小kernel时保留原归约次序与舍入点，并把这类变换和会改变批组成的变换分开。

循环模型每个token重复共享层，小kernel成本也随循环重复。把多个host提交合为一次，并未必消除这些kernel；作者RTX5090 batch1实验中，提交数6→3时Ouro TPOT为16.2→16.3ms。要减少GPU细粒度工作，需要真正融合运算，同时核结果条件。

浮点的关键差异发生在中间值。令 $\operatorname{rnd}$ 表示舍入到目标格式， $r$ 为相加前的残差， $w$ 和 $n$ 为乘积的两个输入量。残差相加时

$$
\operatorname{rnd}(r+w n)\quad\text{与}\quad
\operatorname{rnd}\!\left(r+\operatorname{rnd}(w n)\right)
$$

去掉舍入操作时对应同一实数运算，保留实际舍入时却可不同；原文75,776个BF16元素中18.4%相差1ulp。即便源码有cast，编译器仍可能消除中间舍入或收缩乘加。作者§4.2在所述融合路径中同时维持PyTorch归约次序，并用PTX转换/乘法保留舍入边界。它依赖原软硬件、shape和批组成，不能推广为跨硬件相同。

在standalone GH200、Ouro1.4B、512随机prompt token/128 greedy输出token、其余released defaults相同的对照中，只开关融合kernel集合，exact在并发1/8/32/128下吞吐分别为unfused的1.55/1.59/1.51/1.11倍。作者报告1014/1014请求整段token与unfused相同；近似融合894/1014相同，且结合run spread未显示可辨速度优势。这里的有限验证不等于所有输入的机器等价证明，也不能把整套引擎的提速都归于这些kernel。

保持局部计算还不等于保持服务结果。Huginn KV压实只改地址时，相同批次233/233请求相同；容量增大后请求被重新分组，309/312相同。按位置与通道确定随机latent噪声，虽消除了cache skip改变抽样次序的问题，GPU full-cache-hit与cold仍只有108/128相同，因为suffix prefill改变GEMM行数。随机性身份、批布局与数值执行是相互衔接的独立条件。

这比“数学等价仍可能浮点不同”的一般提醒增加了可操作的检查：先固定逻辑依赖和随机性身份，再比较相同输入/批组成的执行，最后单独测容量/调度变化导致的重新分组。现有artifact缺部分原日志，线上还保留未解释abort；不由这组结果宣称生产稳定、任意输入或跨硬件bitwise。源码固定版本与配置仍待11-12复核。

## Contextual-compatibility

**2026-11-06 新增 AI 候选解释。** 非前缀复用不只会错在位置，也会错在状态原来依赖了什么前文。[Peng、Tang 与 Jia 的 v1 预印本](../sources/paper-nonprefix-cache-repair.md)把“目标块接近 full KV”与“目标块适合当前复用前文”分开。目标块数值完全来自完整计算，也可能和混合上下文不兼容。

把文档块各自独立编码时，其 KV 缺少完整串联输入中的跨块条件化。修正 RoPE 位置可以对齐位置关系，却不会自动补回这些内容依赖。若只把目标块换成 full 计算得到的 KV，这块状态依赖的是完整前文，而前面保留的其他块仍是独立复用状态。另一种修法是在当前复用前文下重算目标块，使它与实际前文相容；后面的块仍保持原复用状态，并没有因此恢复整个序列的精确计算。

主要实验用 Qwen3-8B（关闭 thinking）、Llama-3.1-8B 与 Mistral-7B-v0.2，BF16、greedy，在 RTX 4090D 24GB 上运行；任务包括 LoCoMo、NQ、TriviaQA 与 Gorilla APIBench。为先研究复用会损失什么，作者构造条件子集 Q*：无上下文时回答错误，而完整上下文在SIM、RAND、OTHER（相似干扰块、同类随机块、跨领域散文）三种配置下都答对。原始评分按 0.5 阈值二值化。因此该子集的 full 得分 1 是筛选定义；其中 19%–100% 的保留损失不能写成总体测试集准确率下降了同样幅度。

以下结果区间采用配对问题的 95% bootstrap 区间。一个关键对照固定了已知的非首块目标。Appendix F Table 33 在每个设置按标识符取前 40 个 Q* 问题，Llama 设置为 30 个，共七个设置。NQ/Qwen 的 40 题中，未修复的保留率为 0.15；只插入 full 目标 KV 仍为 0.15；在当前复用前文中重算目标则为 0.53。后者相对插入 full 的增量为 0.38，区间 [0.23,0.53]。这里“保留率”是原文按条件问题的二值任务得分衡量，不是 token 精确相同率。

局部距离进一步揭示为什么“更接近 full”不足以决定修复优劣。重算目标相对 full 的中位相对 L2 距离为 0.26，未修时为 0.36；插入 full 在这个局部指标上的距离当然是 0，却没有更好的任务结果。数值接近只比较目标块本身，没有包含它与其余状态的一致性。这个干预对照支持上下文兼容的机制解释，尚未唯一识别所有底层因果因素。

Table 34 在相同的 270 个问题上改变较早块是否也来自 full：只插 full 目标、较早块仍 reuse 时，平均增量为 0.11，区间 [0.06,0.17]；较早块一起 full 时为 0.25，区间 [0.20,0.31]；交互量为 0.14，区间 [0.08,0.20]。这表明目标修复的效果依赖前文状态，不能把各块收益独立相加。它仍使用已知目标，是诊断性 oracle 对照，不是部署中已经知道该修哪块的成功率。

真实选择规则还要支付寻找目标的代价。原文在约 5% token 预算下，用 BGE-M3 检索选择块、将其移到问题之前，再重算；这个流程同时改变选择、位置和状态。相对 InfoFlow-style 的九个 QA/API 设置中，未校正比较六项改善，Holm 校正后五项；与同样重排 token 的对照比，分别为四项与三项。在 LoCoMo 的 7–8B 设置和 5% token 预算下，优先重算目标或检索会话未显著胜过各设置在开发集选出的 token 级规则；长会话可能超过预算，优先修所选会话也不表示总能重算整块，检索错误时也可能更差。部分 baseline 是简化实现，不能据此排名各原完整系统。

新增理解是：近似复用的修复对象应包含它依赖的上下文状态，而不只是一个局部向量的误差。[此前的近似复用](#approximate-reuse)给出质量义务，本节进一步给出其失效机制与干预对照。5% token 预算不是等 GPU 时间，已知目标实验也不含现实目标选择难度；本轮未审源码或复现。研究与启发价值均高、条件化实验证据可靠性中等，下一步需要无 oracle、同负载的质量与时延联合比较。
